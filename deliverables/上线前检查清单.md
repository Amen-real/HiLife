### A1 ICP 备案 —— 全链路最长项，建议今天就启动 [平台]

自 2023 年 9 月起，所有境内小程序**必须完成工信部 ICP 备案**才能提审、上线；未备案的存量小程序会被下架。这是国家层面要求，**与是否使用云开发/云托管无关**（云开发免除的只是「服务器域名配置」，不是备案本身 —— 这是最常见的误解）。

- **入口**：微信公众平台 → 设置 → 基本设置 → 小程序备案 → 去备案（未上架小程序首页也会直接显示「去备案」）
- **周期**：平台初审 1–2 工作日 → 工信部短信核验（收到后 **24 小时内**必须去 beian.miit.gov.cn 填验证码，超时自动驳回重排）→ 管局审核 1–20 工作日。**整体 7–20 工作日**，快则一周、慢则三周。
- **个人主体材料**：身份证正反面（原件拍摄，不能拍复印件/隔屏拍）、本人手机号、绑定**本人银行卡**的微信号（人脸核身用）、**应急联系电话**（必须与手机号不同，系统会拦截重复填写）。
- **主体一致性**：备案主体必须与小程序注册主体 **100% 一致**。个人主体的备案数量上限是 5 个。
- **不要多平台同时提交**，会触发「主办者冲突」。

**备案时「服务内容标识」怎么选**（个人主体不可选经营性质、企业/单位性质、涉及前置审批的内容）：

| 候选 | 适用性 | 说明 |
| --- | --- | --- |
| 工具 → 健康管理 | ✅ **首选** | 官方口径即「身高、体重等健康数据记录，仅限记录，不能涉及医疗诊断」——与本项目完全吻合 |
| 体育 → 在线健身 | ✅ 可叠加 | 「健身运动的在线学习/指导」，动作库与训练指导落在这里 |

**备注栏必填（20–200 字），建议直接用这段**：

> 本小程序为个人开发的健身记录工具。主要功能：健身动作库查询与动作要领学习、每日训练打卡记录、训练组数与次数记录、体重数据记录与趋势查看、饮食热量记录。所有数据仅保存在用户本机，不上传服务器、不共享给第三方。不提供医疗诊断、在线问诊、药品或保健品销售、课程售卖、用户间社交与内容发布功能。

5. ✅ **[代码] 已修（2026-09-29）真机反馈「拍照识别很慢 / 经常识别不出来」** ——
   根因四条，**没有一条是「模型不行」**：
   - **上游错误被一律抹成「照片问题」**。旧 `vision_llm.py` 用 `raise_for_status()`，401/429/400/5xx
     全塌缩成 `VISION_FAILED` ⇒ 用户拿到的永远是「换一张更清晰的照片再试试」，
     而密钥失效 / 额度用尽 / 模型未开通**重拍一百次也没用**。这正是「经常识别不出来」的来源。
     现改为 `_code_for_http()` 分档 + `LLMError.code` 原样透出：
     `VISION_AUTH`(401/403) / `VISION_QUOTA`(429) / `VISION_MODEL`(400) / `VISION_UPSTREAM`(5xx) /
     `VISION_TIMEOUT`（各自对应「用户能做什么」，`USER_TEXT` 是唯一文案真源）。
   - **超时倒挂**。服务端单次上游超时 120s **大于**客户端轮询窗口 60s ⇒ 服务端还在算，
     客户端已经先放弃并弹一句笼统超时，**真实的 `code` 永远到不了用户眼前**，
     等于把上面那套分类白做了。现为 服务端 `REQ_TIMEOUT = 50s` < 客户端 `POLL_DEADLINE_MS = 70s`
     （守卫 `[E1b]` 断言这个方向，并用倒挂/正常两个样本证明判据不是恒真）。
   - **任务丢失被误判成照片问题**。内存 `TASKS` 是实例本地的，实例重启/缩容即丢；
     旧实现任务找不到时不带 `code` ⇒ 又被兜底成「重拍试试」。现 `app.py` 给 `VISION_TASK_LOST`，
     客户端**自动重提一次**（识别是只读的，不会产生重复记录，代价只是一次调用费）。
     ⚠️ 因此云托管**必须保持单实例**（`server/app.py` 的 `TASKS` 处有说明）。
   - **感知延迟**。整页只有一句静态「AI 识别中…」，等 20s 得不到任何新信息，
     体感就从「慢」变成「卡死」。现每秒刷新「已等待 N 秒」+ 三段式阶段文案（8s / 20s 升级），
     并补上**取消出口**（窗口最长 70s，没有出口就是把用户困住，而慢速档文案里写着
     「可以返回后手动填写热量」—— 没有返回入口，那句话就是实现不了的承诺）。
     另两项提速：轮询由「固定 2s × 30 次」改为「首轮 0.6s、每轮 +0.7s、2s 封顶」，
     常见耗时省 1~2s；`PROMPT` 限制 `items` 最多 4 项（输出 token 数直接决定生成耗时）。
   - 失败弹窗的「重试」只在**重试有用**时出现（`RETRYABLE` 对照表）：给一个注定失败的按钮，
     用户会连点几次、每次等满窗口，最后判定「这功能就是坏的」—— 比不给更伤。
   - 守卫扩到 `[E]`/`[F]` 两节（`verify-vision-result.cjs` 共 142 断言），
     并逐条做**坏状态注入自检**（把真实文件改坏后重跑，7/7 命中才认账）。

### B8 识别结果页顶部被状态栏压住、点不到 —— ✅ 已修复（2026-09-29，真机反馈）

2. 13 个页面用 `<nav-bar>` 组件，其 `.nb-fixed` 是 `position: fixed` ⇒ 天然免疫压缩。

### B9 顶部「靠右控件」与微信系统胶囊重叠 —— ✅ 已修复（2026-09-29，真机反馈）

**现象**：B8 修完（顶栏从状态栏里救出来了）之后，真机立刻报出**下一个**遮挡者 ——
识别结果页的「完成」按钮与微信自带的「**··· ⊙**」（更多/关闭）胶囊叠在一起，点下去弹的是微信菜单。

**根因**：系统胶囊是**微信自己渲染**的。它不进 WXSS 布局树、不参与 flex、`z-index` 对它无效 ⇒
页面把自有控件摆进它那一格，触摸就被系统截走，**按钮完全点不到**。全仓此前**零处避让逻辑**
（`grep getMenuButtonBoundingClientRect` → 0 命中），所以这不是"某个页写错了"，而是一处**空白**。

**关键几何性质**（决定了修法，改之前先读）：

1. 胶囊**贴屏幕右缘**渲染 ⇒ 只要自有控件的**右边界落在胶囊左边界之左**，二者就永不重叠，
   **与纵向位置无关**。所以解法是**横向让位**，不是"把按钮往下挪"。
2. 胶囊宽度随机型／系统版本变化（约 87~96px），右边距也不固定 ⇒
   **拍一个 rpx 常量在窄机型上必然再次重叠**，必须实测。
3. 需要预留的内缩 = 屏幕右缘 → 胶囊左缘的距离 + 一个呼吸间隙（8px）；
   这个量**只由胶囊自身决定，与屏幕宽度无关**。

**修法**：新增单源 `utils/navMetrics.js`（`statusBarHeight()` / `capsuleRect()` / `topRightInset()` / `topRightStyle()`），
页面侧只做两件事：`onLoad` 里 `this.setData({ navInsetStyle: navMetrics.topRightStyle() })`，
顶部那一行挂 `style="{{navInsetStyle}}"`（只含 `padding-right`，长写覆盖简写的一侧，不动该行其它 padding）。
测不到胶囊（低版本基础库 / 测试环境）时退化为保守常量 112px —— **宁可多留一点都不许少留**。

| 位置 | 改动 | 说明 |
| --- | --- | --- |
| `utils/navMetrics.js` | **新增** | 胶囊让位的唯一真源；状态栏高度也一并向这里收口 |
| `food-scan.wxml` `.cam-top` | 挂 `style="{{navInsetStyle}}"` | 取景态闪光灯（⚡）靠右，正在胶囊那一格 |
| `food-scan.wxml` `.r-nav` | 挂 `style="{{navInsetStyle}}"` | 结果态「完成」——**用户报的就是这一处** |
| `food-scan.wxml` `.h-nav` | 挂 `style="{{navInsetStyle}}"` | 历史态「清空」——同一格，一并修（漏了就是下次真机再来一次） |
| `food-scan.js` `onLoad` | 注入 `navInsetStyle`；状态栏高度改从 `navMetrics` 取 | 删掉本页自己那份 `getWindowInfo`，避免两套兜底值各走各的 |
| `components/nav-bar/nav-bar.wxml` | 右侧 slot 加**警示注释**（零功能改动） | 该 slot 正对胶囊、当前 16 页无人填充；注释给出接入 `navMetrics` 的两行写法，防将来踩坑 |

`workout` 的「完成训练」虽也在右上，但它落在 `nav-bar` 之下（y ≥ 状态栏高 + 44px），**不进胶囊纵向带**。

**守卫**：`scripts/verify-top-inset.cjs` 新增 `[G]` 段 + `[D]` 补一条（共 34 断言，全量 18 脚本 0 失败）：

  兜底分支（112px），并证明两个分支**返回值不同**（⇒ 判据真的读了胶囊，不是常量）；

### B10 顶部行与微信系统胶囊「没对齐」 —— ✅ 已修复（2026-09-29，真机反馈）

**现象**：「取景页面的返回按钮和闪光灯按钮没有对齐微信自带胶囊，识别完成页的返回和完成按钮也是一样」。

**先分清两件事**：这与 B9 是**两个方向、两个问题**，别用同一招 ——

| | 问题 | 方向 | 失配后果 |
| --- | --- | --- | --- |
| **B9** | 控件与胶囊**重叠** | 横向 | 触摸被系统截走，**点不到** |
| **B10** | 行与胶囊**没对齐** | **纵向** | 点得到，但一眼看着错位 |

**根因**：同一类病 —— **又拿手调 rpx 常量摆位**，谁也跟不上胶囊。逐行量化（390px 宽 / 状态栏 47px / 胶囊 y=[53,85]、中线 69）：

| 位置 | 修复前 | 偏移 | 行高 vs 导航带 |
| --- | --- | --- | --- |
| 取景态 `.cam-top` | `padding: 90rpx 36rpx 0` ⇒ 内容中线 65.5px | **偏上 3.5px** | — |
| 结果态 `.r-nav` | 占位块后接 `padding: 16rpx`，行盒 y=[47,96.9] 中线 72.0px | **偏下 3.0px** | 49.9px ≠ 44px |
| 历史态 `.h-nav` | 与 `.r-nav` 同款写法 | **偏下 3.0px** | 49.9px ≠ 44px |

**修法**：行高不再拍常量，改按胶囊实测 —— 让顶部行做成**以胶囊中心为对称轴**的带状：

```
导航带高 = (胶囊上沿 − 状态栏) + 胶囊高 + (胶囊下沿 − 状态栏)
         = 2 × (胶囊上沿 − 状态栏) + 胶囊高        ⇒ 「行中心 == 胶囊中心」恒成立
```

⚠️ **不能用字面量 44**：44 只在「胶囊顶 − 状态栏 = 6px」时成立，而该差值随机型变
（iPhone X 类差 4px ⇒ 40、大胶囊安卓差 8px ⇒ 52）。守卫 `[H1]` 用 4 个机型档案把这条不变量钉住。

| 位置 | 改动 |
| --- | --- |
| `utils/navMetrics.js` | 新增 `navBarHeight()`（上式，测不到胶囊兜底 44）；新增 `topRowStyle()`（流式行：`height` + `padding-right`）与 `overlayRowStyle()`（绝对定位覆盖层：额外自带 `top`）；原 `topRightStyle()` 由这两者取代 |
| `food-scan.wxss` `.cam-top` | `padding: 90rpx 36rpx 0` → `padding: 0 36rpx`；加 `box-sizing: border-box`；兜底 `top:44px; height:44px`（注入前用） |
| `food-scan.wxss` `.r-nav` / `.h-nav` | `padding: 16rpx 32rpx` → `padding: 0 32rpx`；加 `box-sizing: border-box; height: 44px`（兜底） |
| `food-scan.wxml` | `.cam-top` → `{{camRowStyle}}`；`.h-nav` / `.r-nav` → `{{navRowStyle}}`（**覆盖层与流式行必须挂对**，挂错就丢 `top`） |
| `components/nav-bar/nav-bar.wxml` | 右侧 slot 的警示注释同步到新键名（旧注释已作废，照抄会写出空样式） |

⚠️ **两条联动陷阱**（守卫 `[H11]` / `[H12]` 盯着，单看 JS 算得再对也会被吃掉）：
① 行内 `height` 必须配 **`box-sizing: border-box`** —— 否则它是**内容盒**高，加上 padding 后总高 ≠ 导航带；

## C 建议（不阻塞上线，1.0 后处理）

### C1 本地存储单键 1MB 上限 [代码]

`app.js:119` 的 `persist()` 把**整个 `globalData`** 写进单键 `uu_fitness_state`。`trainingLogs` / `meals` / `weightRecords` 只增不减。

建议：1.0 之后拆键（如 `state_settings` / `state_logs` / `state_plan`），或至少加写入失败兜底 + 提醒用户导出。

### C2 AI 功能表述 [代码]

个人主体**不可做「AI 生成图片」**类目。本项目是**识别**不是生成（拍照 → 返回食物名与热量），属安全区。但建议类目备注与页面文案统一写「**AI 拍照识别**」，避免出现「AI 生成 / AI 创作」字样被误判为深度合成类。

### C3 主包余量 433 KB —— 健康，但结构值得优化 [代码]

`utils/exercises.js` 单文件 404 KB，占主包 25%。1.0 之后可考虑把动作库切到分包。
（主包实测 1615 KB / 2048 KB。B8~B10 与 B7-4 的改动全是 CSS/JS 文本，增量可忽略；
守卫脚本走 `scripts/` folder 忽略规则，不进包。回归用 `node scripts/scan-main-package.cjs`。）

### C4 `uploadWithSourceMap: true` [代码]

上线包不需要 sourcemap，关掉可略微减小上传体积（不影响主包 2MB 限制，属清理项）。

### C5 个人信息的「敏感信息」标注 [平台]

身高 / 体重 / 年龄属**敏感个人信息**。隐私指引里要把**用途、存储位置（仅本机）、是否共享（不共享）**写清楚。「仅本机存储」是本项目的强合规优势，务必显式写明。
