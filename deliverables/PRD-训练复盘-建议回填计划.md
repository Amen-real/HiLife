# PRD · 训练复盘「下次训练建议回填计划」

> 视角：ProductManagementExpert ｜ 模块：训练复盘（数据页）→ 闭环增强
> 状态：**已实现（含降重扩展 v2）** ｜ 关联分析：`deliverables/训练复盘架构与功能分析.md` §3.2-①（P0 闭环项）
> 红线：不参考已淘汰的 `12-review.html`；所有计算走 `utils/trainingStats` 单源；组件只组装、不现算。
> 落地记录：`utils/trainingStats.nextSessionSuggestion` + `components/training-review/*` + 守卫 `scripts/verify-training-review.cjs`（216 项）。

## 1. 背景与问题（Why）

用户练完一场，复盘页会给出一句话 verdict + 逐动作文案建议（`stats.actionAdvice`：如"状态轻松 · 下次可加重 2.5–5%"）。**但这是不可执行的文本**——要真正应用，用户得手动打开计划页、找到对应动作、改重量/次数。摩擦极高，导致：

- 建议被忽略，训练变成"凭感觉加量"，无法**刻意渐进**（progressive overload）。
- 复盘沦为"终点"（看一眼就走），而不是"回路"的一环（看→调计划→再练）。

竞品对标：Strong / Fitbod 的留存核心正是"逐动作渐进负荷建议 + 一键应用"，这是 HiLife 相对 Keep（堆图表）的差异化方向。

## 2. 目标与范围

**目标**：把复盘的建议变成"可一键应用到计划"的刻意渐进，闭合 记录→洞察→行动 回路。

**非目标（Non-goals）**
- 不做 AI 全自动重写整份计划（数据少时易误导，且越权）。
- 不做社交/分享建议。
- **不自动应用**——建议须用户确认点按（建议是咨询性质，最终决策权在用户）。
- 不改训练执行页逻辑，只改计划的"目标值"。
- 不采用任何来自已淘汰 `12-review.html` 的布局/字段。

## 3. 用户故事

- 作为被计划驱动的用户，我希望复盘直接告诉我"下周这个动作加多少重量/次数"，以便不用自己算。
- 作为被计划驱动的用户，我希望一键把上述调整写进计划，以便进度是刻意的。
- 作为自由训练用户，我希望建议基于我自己的历史，以便仍获得渐进指导。
- 作为谨慎用户，我希望应用前能改一下建议值，以便不完全照机器来。

## 4. 方案设计

### 4.1 建议引擎（全部落在 `utils/trainingStats`，新增纯函数）

新增 `nextSessionSuggestion(actions, logsDesc, idx, activePlan)`，复用既有 building blocks，**不在组件里现算**：

对当前场次每个动作 `a`：
1. 取当前表现：`peakWeightOf(a)`（峰值重量）、`bestSetOf(a).reps`（峰值次数）、`setsOf(a).length`（组数）、`avgRpeOfActions([a]).avg`。
2. 定基线 `baseline`：
   - 若 `activePlan` 存在且含同 `actionId` 动作 → 基线 = 计划目标 `{ setsCount, reps, weight }`（**计划优先**）。
   - 否则 → 历史基线：用 `findPrevVol` / `loadIndexByKey` 取上一场同键动作的"可比容量"。
   - 都没有 → 标记 `firstSession`，返回首训提示。
3. 定增量（沿用 `DELTA_*` 阈值精神，**加重与降重共用同一道达成闸门**）：
   - `rpeAvg ≥ 9` → **减载**：降至 ≈ -10%（2.5kg 阶梯取整），见 §4.5。
   - 计划高于本场实际 且 `rpeAvg ≥ 8` → **降重**：降至不超过本场实际峰值，见 §4.5。
   - `rpeAvg ≤ 6` 且（命中计划 或 历史容量≥2场向上）→ 建议重量 **+2.5%（按 2.5kg 阶梯取整，单次 ≤ +2.5kg）**，次数/组数维持；若自重动作（`capacityOfAction` 退化为 Σ 次数）→ 建议 **+1 次**，绝不加重。
   - 其余 → "保持容量稳步推进"，零增量。
4. 输出每动作：`{ key, name, fromW, toW, fromReps, toReps, fromSets, toSets, reason, editable }`。

### 4.2 组件呈现（只组装，复用现有 `training-review` 组件）

- 在「本次训练」tab，verdict 下方新增 **「下次训练建议」卡片**（不新增 tab，保持两 tab 既定结构）。
- 每行：`动作名` + `当前 60kg×8 → 建议 62.5kg×8` + 可编辑输入框（预填建议值）。
- 卡片底部「应用到计划」按钮：
  - 有激活计划且含匹配动作 → `store.updatePlan(plan.id, { actions: 合并后 })`，仅更新匹配动作（未匹配动作原样保留），**不调用 `setActivePlan`**（绝不改动激活指针）。
  - 无激活计划 / 无匹配 → 弹窗提示"先创建或导入含该动作的计划"，不静默失败。
  - 全部为"维持/保持"（无可执行增量）或无历史 → 按钮置灰。
- 应用成功 → `wx.showToast('已更新计划')`；可选 `wx.switchTab` 到计划页或就地刷新。

### 4.3 数据契约（真实字段，已核对）

- 计划动作：`{ actionId, name, nameZh, part, category, setsCount, reps, weight, rest }`（`store.js:193`）。
- `store.updatePlan(id, patch)`：浅合并 patch，传 `actions` 即整体替换该计划动作数组（`store.js:207`）。
- 匹配键：优先 `actionId`；日志动作已存 `id`（`workout.js` 落库），与计划 `actionId` 对齐；历史日志无 id 时回退 `actionKey`（id+器械）。

### 4.4 关键边界决策

- **计划 `reps` 是字符串**（如 `'8-12'`）：仅当计划 reps 为单一整数时，把建议次数写回；否则**只更新 `weight` 数值**，保留 `'8-12'` 区间语义，避免破坏范围写法。
- **模板计划（`programId` 存在）轮转**：只应用到"当前激活训练日"，不跨整个 program 改写。
- **自重动作**：永不加重，只 +1 次 / +1 组。

### 4.5 降重（减载）—— v2 扩展

**为什么做**：只有"升"的方向是不完整的。① 累积疲劳需要 deload（训练科学标准操作）；② 计划目标可能被设得过高（含历史上"点一次涨一次"的 bug 遗留），需要一个数据驱动、能自动收敛的下调出口；③ 在补上计划页重量输入前，计划重量**唯一**的写入途径就是这张卡，"只升不降"等于计划重量只增不减。

**触发（从严，门槛高于加重）**——加重只要 `rpe ≤ 6` 一个条件；降重要求"练了但顶不上去"或"已经很吃力"：

| 触发 | 条件 | 目标值 |
|---|---|---|
| 疲劳降载 | 本场 `rpeAvg ≥ 9` | `roundPlate(本场峰值 × 0.9)` ≈ -10% |
| 计划过高 | 本场未达计划重量 **且** `rpeAvg ≥ 8` | `floorPlate(本场峰值)` = 不超过本场实际 |

**不接受单场状态波动**：本场未达计划但 `rpe < 8`（只是没顶上去）→ 仍只提示"先按计划再练"，不降。

**幂等口径（与加重同源）**：增量基数一律取 **本场实际峰值**（不可变历史），不取计划当前值。降重为**向下取整**（`floorPlate`）——否则会出现"降了其实没降"。

**同一道闸门、双向自适应**：`planW > target` 才下发降重；降完后 `planW ≤ target` → 闸门解除 → 重算转"维持" → **不可再降**。因此不需要额外的"降重次数"状态，天然收敛（防一路往下掉）。

**边界**：自重动作（无重量）不适用，转"维持"；无匹配计划时降重没有可写目标，不给按钮。

### 4.6 计划页重量手动入口 —— v2 扩展

计划页此前**没有重量输入框**（`plan.wxml` 无 `weight` 绑定，`savePlan()` 只存 `name/goal/level/daysPerWeek/desc/actions`），用户对计划重量没有任何手动出口。v2 补上：

- 已选动作行新增 `kg` 输入（`onActionWeight`），与既有 `组` / `次` 并列；`weight` 以**字符串**存储，与 `plan.actions[].weight` 同型（空串 = 未设定，占位符显示 `—`）。
- 计划详情行同步展示重量：`3 组 · 8-12 · 60kg`（无重量则整段省略，不显示 `0kg`）；并把该行 `wx:key` 由 `name` 改为 `k`（同名动作重复时不再错位）。

## 5. 验收标准（Acceptance Criteria，可测）

- **AC1 建议正确性**
  - 给定 `rpeAvg ≤ 6` 且同键历史≥2场向上 → 建议重量 +2.5–5%（2.5kg 取整），次数/组数维持。
  - 给定 `rpeAvg ≥ 9` → 无重量/组数/次数增量，reason 含"维持容量"。
  - 给定 `6 < rpeAvg < 9` → 建议"保持容量稳步推进"，增量为 0。
  - 给定首训（`buildVerdict` kind=`first`）→ 卡片显示"完成首次训练后给出具体加重建议"，应用按钮置灰。
- **AC2 计划匹配优先级**：激活计划含同 `actionId` 动作时，基线取计划目标而非历史；无匹配/无计划时回退历史；再无则首训提示。
- **AC3 应用写入正确**
  - 点「应用到计划」仅更新该计划内匹配动作；未匹配动作不变。
  - **`activePlanId` 不被改动**（`setActivePlan` 不得被调用）。
  - 应用后 `store.getActivePlan().actions` 反映新值，`store.persist()` 已调用（重载后仍在）。
- **AC4 自重处理**：自重动作建议 +1 次 / +1 组，绝不加重。
- **AC5 架构/守卫合规**
  - 建议计算为 `trainingStats.nextSessionSuggestion` 纯函数（无 `wx`/`store` 依赖，可 node 直跑）。
  - 在 `scripts/verify-training-review.cjs` 新增断言段：函数存在且纯；AC1–AC4 场景输出符合预期；建议 `setData` 字段全为字符串/数字，通过既有 [I] 递归扫（无 `[object Object]` 回归）。
- **AC6 交互**：无可执行增量或无计划匹配且无历史时，应用按钮置灰；应用前用户改过的预填值，以用户改值为准写回（非原始建议值）。
- **AC7 降重（v2）**
  - `rpeAvg ≥ 9` 且有匹配计划 → 建议降重，`deload=true`、箭头 `↓`、目标 = `roundPlate(本场峰值×0.9)`。
  - 本场未达计划重量且 `rpeAvg ≥ 8` → 建议降至不超过本场实际（`floorPlate` 向下取整）。
  - 本场未达计划但 `rpeAvg < 8` → **不降**，仍提示"先按计划再练"。
  - **幂等**：按建议回填后再重算 → `actionable=false`（不可再降）。
  - 自重动作 / 无匹配计划 → 不降。
  - 端到端：回填后 `plan.actions[].weight` 下调到位，`activePlanId` 不变。
- **AC8 计划页重量入口（v2）**：已选动作可编辑重量并落库（字符串型）；计划详情显示重量；动作行 `wx:key` 唯一。

## 7. 风险与依赖

- **数据层天花板（依赖）**：计划与日志全在本地 `wx.setStorageSync`，换机即丢。建议回填再顺手，也救不回卸载流失——**应先于本功能做云 DB 同步（基线 P0-1）**。
- **reps 字符串语义**：见 §4.4，只改数值型 weight，避免破坏 `'8-12'` 区间。
- **模板轮转耦合**：只改激活日，勿动 `advanceActivePlan` 逻辑。
- **口径回归**：新增 `nextSessionSuggestion` 必须走单源，禁组件内现算；过 [I] 守卫。

### 8.1 已实现的防发散设计（写进红线）

> 「可反复点按的写回型建议」的建议值**只能依赖不可变的历史事实**（本场实际达成），**不能依赖被写回的目标本身**（计划当前值）；否则 写回 → 重算 → 再写回 会形成正反馈发散。加重会"越加越多"，降重会"越降越低"。
> 再加一道**达成闸门**，让"没做到"成为无法继续加重的自然终点、"已降到目标"成为无法继续降重的自然终点 —— 同一道闸门双向收敛。
