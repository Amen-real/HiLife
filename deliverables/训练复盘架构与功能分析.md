# 训练复盘（数据页）· 架构与功能分析（产品经理视角）

> 视角：ProductManagementExpert（价值判断官，Why 优先，必写 Non-goals，指标可衡量，竞品客观）
> 基线（已确认、可参考）：当前实现 `components/training-review/`（两 tab 组件，内嵌 `pages/list` 的"数据"tab）、数据层 `utils/dateRange` + `utils/trainingStats` 单源；架构文档 `ARCHITECTURE.md`；整体基线 `产品需求分析与建议.md`。
> 注：`12-review.html` 为已淘汰方案，不采纳其任何设定（四 tab / kcal / RPE 环 / 训练量柱图），本文档的功能建议一律从用户需求与竞争对标推导。
> 结论先行：骨架健康，最大机会不在"补被淘汰稿的图表"，而在 **把复盘从"终点"做成"回路"（建议回填计划）+ 先补数据层结构性风险（云 DB 同步）**。

## 0. TL;DR（一句话给决策人）

1. 数据层已抽到 `dateRange`/`trainingStats` 单源、口径（自然周/同动作对比/周目标优先级）已用红线 + 守卫脚本守住 —— **架构地基是好的，别动它**。
2. 当前已落地设计就是**两 tab（本次训练 / 进步趋势）**，这是既成事实，不是"未完成的半成品" —— 不要为了某份淘汰稿去补四 tab / kcal / RPE 环。
3. 复盘目前是"终点"（练完看一眼），应变成"回路"（看→调计划→再练）—— **补"下次训练建议回填计划"是差异化的关键一跳**（对标 Fitbod 的 progressive overload）。
4. 数据层天花板（本地 Storage，换机即丢）是结构性风险，**应先于功能扩张做云 DB 同步**（基线 §4.1）。
5. 功能扩展必须靠"用户需求 + 竞争对标"论证，而非某份稿子——下文每条都标注推导来源。

## 1. Why —— 用户在复盘上的"待完成任务"(Jobs to be Done)

用户练完那一刻的真实问题，按频率排序：

| # | 用户内心问题 | 复盘要回答 | 当前覆盖 |
|---|---|---|---|
| 1 | 这次练得怎么样？ | 即时反馈（verdict + 3 stat） | ✅ 已有 |
| 2 | 比上次/比基准进步没？ | 纵向对比（同动作 verdict、比上次 chip） | ⚠️ 部分（藏在文案，无可展开曲线） |
| 3 | 下周该加重量还是换动作？ | 可执行建议 → 回填计划 | ❌ 缺（仅"下次建议"文案，不可执行） |
| 4 | 这一周/这一周期达标没？ | 节律锚点（周完成度环、6 周努力度） | ✅ 已有 |

**复盘的存在意义 = 把"记录"变成"看得见的进步"，制造"明天还想回来看看"的理由（留存钩子）。** 它不该是又一个图表仪表盘，而该持续回答上面 4 个问题。

## 2. 架构角度 (Architecture)

### 2.1 现状架构（已较好，应坚持）

```
入口层   pages/list (tab=review, 透传 focusDate 与记录页选中日期联动)
   │
组件层   components/training-review  ── wx:if/wx:elif 两 tab（销毁重建，状态干净）
   │        · 本次训练：verdict + 场次切换 + 3 stat + 逐动作表现 + 训练感受
   │        · 进步趋势：周完成度环 + 关键动作 top3 + 近6周努力度 + 吃力引导
   │
逻辑层   training-review.js 只做"取数→组装 setData"，计算全委托：
   │        utils/trainingStats（单源常量 EST_KCAL_PER_MIN/DELTA_*/buildVerdict 四分支）
   │
口径层   utils/dateRange（自然周半开区间）· utils/trainingStats.weekTargetOf（周目标优先级）
   │
数据层   store.trainingLogs（saveWorkout 产出 setsDetail[]: reps/weight/trainSec/restSec/rpe）
            + planId/programId 归属 + profile.weeklyTarget + activePlan.daysPerWeek
```

**已验证的良好实践**（务必保留）：
- 计算与渲染分离：`trainingStats` 不依赖 `wx`/`store`/`getApp`，可被 node 直跑、可被 `scripts/verify-training-review.cjs` 守卫覆盖。
- 口径单源：任何"本周/上周/周目标/对比"都不在组件里现算，走 `dateRange`/`trainingStats`（红线守住）。
- 组件内聚、`list` 页薄：list 只负责 tab 切换与 `focusDate` 透传，复盘全部自包含。

### 2.2 建议的架构演进（不破坏现有两 tab）

新增能力以 **tab 内扩展或复用 `buildVerdict` 分支** 实现，不重写现有组件；所有计算仍走单源。

```
数据层   store.trainingLogs / planId / profile.weeklyTarget / activePlan.daysPerWeek
   │  （单源，禁组件现算）
口径层   utils/dateRange (自然周) · utils/trainingStats (verdict/容量/周目标/kcal/estKcal)
   │
组件层   components/training-review
            ├ 本次训练（保留）
            ├ 进步趋势（保留，接周期化）
            └ 建议在"本次训练"内增"下次建议→回填计划"入口（非新 tab）
   │
入口层   pages/list (focusDate 联动) · pages/plan (下周建议回填) · 分享卡
```

- **计划流归属打通**：复盘从 `log.planId` 反查 `activePlan`，回答"这场是按哪个计划练的、下一场计划要求什么"，为"建议回填"铺路。
- 不引入"滚动/基准对比"独立 tab 的硬承诺——当前两 tab 已是既定设计；若未来要扩展，也须先有用户需求/竞争论证，而非对照淘汰稿。

## 3. 功能角度 (Features)

### 3.1 已实现（应保留，勿回退）
- 本次训练：一句话 verdict（同动作对比，四分支 `first/common/fallback/none`）、场次切换、3 stat（时长/训练量/平均吃力）、逐动作 best/setsMeta/比上次 chip/下次建议、训练感受聚合。
- 进步趋势：本周执行（周完成度环 + 自然周 + 计划优先 + 周目标就地改，计划决定则锁）、**个人纪录**、**近 6 周训练量**、关键动作训练量趋势（**自动前 3 + 可切换自选**）、吃力引导、场次不足钩子、空态 CTA。
- 联动：`focusDate` 与记录页日期筛选联动。

> 进步趋势的口径于 2026-09-14 改版（纵轴 RPE → 训练量、柱高 topW → 容量、新增个人纪录），见 §3.4。

### 3.2 应补强的功能（基于用户需求与竞争对标推导 —— 非来自淘汰稿）

每条都标注推导来源，便于决策时判断优先级：

1. **下次训练建议回填计划（来源：用户需求 #3 + 竞争对标 Fitbod）**【最高价值】
   当前只给"下次建议"文案，不可执行。应基于本场 verdict/容量变化，给出"下周该动作 +X kg / +1 组"的可执行建议，一键跳 `pages/plan` 编辑。这是把复盘从"终点"变"回路"的关键一跳，也是 HiLife 相对 Keep 的差异化（可执行而非堆图表）。
   → **已落地**（含降重/减载），见 `PRD-训练复盘-建议回填计划.md`。
2. **任意动作的历史曲线（来源：用户需求 #2，进阶用户）**
   复盘页已给 top3 迷你柱，并支持**自选关心的动作**（自动前 3 + 可切换，2026-09-14 落地，见 §3.4-v2）。仍缺的是"全程曲线"：应支持点开/搜索任意动作看完整历史。入口建议收敛到 `pages/action-detail`（该页已有「历史记录」列表，加趋势图即可），避免复盘页承载二级详情。
3. **周期化视角（来源：整体基线 Phase 2 周期化）**
   接 `pages/cycle` 周期模板，复盘增加"本周期累计/达成"，而不只有自然周，呼应计划页 A/B/C 轮转。
4. **分享卡（来源：基线 P2-9，个人主体合规允许）**
   生成带完成度/数据的图片供外部分享（个人主体不能做社交关系链，但可走图片分享）。

### 3.3 可选探索（需先验证需求，勿默认做）

以下来自"用户可能的需求"，但**当前无已确认设计或强论证**，列为探索项、不进主路径：
- **本场消耗 kcal 展示**：用户"想和饮食对账"是真实需求（基线 §3-3 智能营养闭环），可把 `trainingStats.estKcal` 作为第三个 stat 候选；但须与饮食 kcal 用同一套 Mifflin-St Jeor 口径，避免"记录消耗 8/min 估算"与"摄入 Mifflin 目标"两套语义打架。
- **更多 tab（滚动/基准对比）**：淘汰稿的四 tab 不采纳；是否扩展以未来用户需求论证为准。

### 3.4 改版记录：进步趋势（2026-09-14）

**触发**：用户反馈"训练复盘页的进步趋势感觉没什么作用"。核查后确认**不是审美问题，是指标选错**——两块图各有一个"零信息"缺陷。

#### 证据（均核对到行）

| # | 症状 | 代码位置 | 机理 |
|---|---|---|---|
| ① | 「近 6 周努力度」六根柱永远等高 | `training-review.js` 旧 `buildWeekly` | 纵轴取**周均 RPE**：RPE 无方向性（高≠进步、低≠退步），数值又被压在 6–9；柱高 = `max(6, rpe×10)%` 只有 60%–90%，容器 `.wk-w-track` 160rpx 下 **7.5→120rpx、7.8→124.8rpx，差 4.8rpx（真机约 2.4px）** |
| ② | 「关键动作」柱高对自重动作全等 | 旧 `buildKeyActions` | 纵轴取 `topW / maxW`；自重动作 `topW` 恒 0 → `maxW = Math.max(1,…) = 1` → 每根柱 `(0\|\|1)/1×100` = **100%**，8 根柱完全等高；且 chip 条件 `s[0].topW > 0` 不成立 → 连涨没涨都不说，只显示「N 场」 |
| ③ | 重量不变、次数 8→12 的进步不可见 | 同上 | 只画峰值重量，丢掉次数维度 |
| ④ | 「进步」在 App 内有两个定义 | 本次训练 tab 用 `capacityOfAction`，趋势卡用 `topW` | 同一页两套口径，用户会先怀疑数据 |
| ⑤ | 叫"进步趋势"却没有 PR | — | 情绪价值最高的一块完全缺失 |
| ⑥ | 「周完成度环」是**执行**不是**进步** | — | 与计划页组头周进度同口径重复，且埋在低频 tab 里 |

#### 决策与落地

- **② 纵轴换成周训练量**（`Σ 重量×次数`；自重退化为 `Σ 次数`）——单调、有量级差；柱上标具体数值。
- **③ 关键动作的柱高与 chip 换成「可比容量」`capacityOfAction`**——与本次训练 tab 同口径（同时解掉 ④ 与 ②）；foot 仍保留可读的「最好一组」，另加一行「训练量 A → B kg」解释 chip 的百分比从哪来。
- **⑤ 新增「个人纪录」块**：每个动作历史最高「单组容量」（重量×次数，自重退化为次数），按最近刷新倒序取 3，近 7 天标「新」，汇总句 = 「近 7 天刷新 N 项个人纪录」/「最近一次破纪录在 N 天前」。只统计练过 ≥2 场的动作（首次记录谈不上破纪录）。
- **⑥ 保留在原处但显式分区**：加 section 标题「本周执行」，与「进步」区在视觉上分工，不再冒充进步。
- **新增冷启动门槛**：场次 < 2 不画趋势图，改为「再练 N 次，就能看到训练量与个人纪录的变化」——1 根柱不是趋势，只会加深"这页没用"的印象。

#### 明确未做（留给下一轮决策）

- **周完成度环挪到「本次训练」tab**：本轮只加了分区标题，未做位置迁移（迁移收益是让趋势 tab 职责更纯，但有布局返工成本）。
- **任意动作全程曲线**：见 §3.2-2，建议落到 `pages/action-detail`（该页已有历史记录列表），不要在复盘页做二级详情。

#### 守卫

`scripts/verify-training-review.cjs` 216 → **260**，新增 `[L]` 段 25 项，把上述「零信息」症状直接写成断言（如"柱高量级差 ≥40"、"自重柱高不得全等"、"仅 1 场不画趋势"），防止后人改回旧口径。

### 3.5 改版记录 v2：关键动作「自动前 3 + 可切换」（2026-09-14）

**触发**：用户要求"关键动作的选择权改成「自动前 3 + 可切换」"。

**为什么必须改**：列表写死 `groups.slice(0, 3)`，排序键是"场次最多"。练得最勤的往往是卷腹、绳索下压这类高频孤立动作，而用户真正想盯的主项（卧推/深蹲）因为轮转到 B/C 组，场次反而排不进前 3 —— 图上看不到自己最在意的进步。

#### 决策

| 项 | 决定 | 理由 |
|---|---|---|
| 默认行为 | 自选为空 → 场次降序前 3（与改版前完全一致） | 不打扰不用这个功能的人，老用户零感知 |
| 卡片顺序 | **跟选择顺序**，不跟场次 | 用户排序即意图；勾"深蹲、卧推"就该深蹲在前 |
| 候选列表顺序 | 恒为场次降序 | 弹层是用来"找动作"的，稳定排序才好找 |
| 存什么 | `actionKey`（动作 id + 器械）数组 | 只存名字会在"同名不同器械 / 两个自建动作重名"时串台（同 §F 段教训） |
| 存哪 | `globalData.keyActionPicks` → `store.get/setKeyActionPicks()` | 与其他偏好同一套持久化；`login()` 备份 / `logout()` 清空，不串号 |
| 上限 | 3（`KA_MAX` 单源常量，自动列表与自选共用） | 卡位是版面约束，不是偏好 |
| 恢复默认 | 一个都不勾 = 空数组 = 自动前 3，不需要单独的"重置"入口 | 少一个按钮少一次解释；弹层另给"恢复自动"快捷键 |
| 落库时机 | 勾选只改内存，点「完成」才落库 | 误触不该改掉配置 |

#### 边界处理

- 选了但**一场都没练过**的动作 → 跳过不渲染空卡；若全无效 → 回落自动前 3 且 `kaCustom=false`（不谎报"自选生效"）。
- 弹层**每次打开**都从已落库选择重建勾选态 → 上次勾了没保存就退出，不会残留。
- 0 场（空态）时候选与计数一并清零。

#### 守卫

`verify-training-review.cjs` 260 → **307**，新增 `[M]` 段 32 项：自动前 3 与自选顺序、无历史 key 跳过、落库去重/限长/非法入参、满 3 拦截与解除、保存后卡片同步、重开丢弃未保存勾选、空态清零；`[H]` 段补 14 项接线断言（含"组件不再写死 `groups.slice(0, 3)`"这条回归锁）。

#### 修复：数据 tab 里抽屉底部按钮被自定义底栏遮挡（同日）

**症状**：在「数据」tab 打开关键动作抽屉，「恢复自动 / 完成」被底部菜单（自定义 tabBar）盖住，点不到。

**根因**：`app.json` 开了 `tabBar.custom = true`，底栏由 `custom-tab-bar` 渲染成**框架级固定层**（`.tab-bar` 自身 `z-index: 1000`）。页面里的弹层 `z-index` 再高也压不住它 —— 项目里既有的两个 tab 页抽屉都是靠**底部留白**避让的（`pages/list` 留 `88rpx + 24rpx`、`pages/plan` 留 `104rpx`）；本组件是从「本次训练/复盘」这种普通页长出来的，只留了安全区，于是搬到 tab 页就露了。

**修复**：组件运行时探测宿主页是否有底栏（`getCurrentPages()` 末页 `getTabBar()` 是否返回实例），只在有底栏时给抽屉补 `padding-bottom: calc(88rpx + 44rpx + env(safe-area-inset-bottom))`（88 = 底栏内容高，44 = 与按钮的视觉间距）。普通页（复盘）保持原样，不白留一块空。

**为什么不直接把 `z-index` 调更高**：这是框架级固定层，不是同层竞争；项目里已有两处先例都选择了留白避让，抬高 `z-index` 只会制造"看起来能压住、真机压不住"的假象。

**守卫**：`verify-training-review.cjs` 307 → **316**，`[M]` 加 M9（tab 页预留 / 底栏未挂载不预留 / 普通页不预留 / Node 环境无 `getCurrentPages` 不抛错），`[H]` 加 4 项接线（wxml 的 `with-tab` 类、wxss 的预留规则、`_hasTabBar` 探测）。

### 3.6 改版记录 v3：删除「本周执行」卡（2026-09-14）

**触发**：用户判定"进步趋势的本周执行卡片感觉没有必要保留"。

**为什么删**：这张卡回答的是"我按计划练了吗"，而「进步趋势」这个 tab 回答的是"我变强了吗"。用户带着进步预期进来，看到的是执行数据——**信息本身没错，是答错了问题**。它埋在"数据 → 复盘 → 进步趋势"三层里，触达率本就≈0，占着版面只会稀释这一页的唯一职责。

**删掉的内容**：周完成度环（conic-gradient）+ 本周训练天数 + 本周平均吃力 + 周目标就地改入口。相应地移除 `data.weekly`、`EMPTY_RING` 常量、`editWeeklyTarget()`，`buildWeekly` 收窄为 `buildWeeks`（只算近 6 周训练量）；WXSS 清掉 15 个专属类（`wk-head/wk-ring*/wk-pct*/wk-meta*/wk-mv/wk-mu/wk-ml/wk-target*/wk-dot/wk-edit`），**保留** 近 6 周柱状图仍在用的 `wk-weeks/wk-w-col/wk-w-track/wk-w-bar/wk-w-val/wk-w-lab/wk-empty`。

**口径未变**：周目标优先级（计划 `daysPerWeek` > `profile.weeklyTarget` > 3）仍由 `trainingStats.weekTargetOf` 单源维护，`[B]` 段 7 项测试照旧跑——它是**口径契约**，不是这个卡的私有逻辑，等首页进度卡落地时直接复用。

**已知副作用（待决策）**：删掉这张卡后，`profile.weeklyTarget` **失去了全 App 唯一的编辑入口**（`store.setWeeklyTarget` 已无任何调用方；`pages/settings` 的「健康数据」页也没有这一项）。二选一：
- **(a) 挪到「我的 → 健康数据」**：与性别/目标体重/身高/年龄/活动水平同页，约 8 行（data + onLoad + 一个 input 处理 + save 里带上）。**推荐**——能力不丢，等首页进度卡上线后再决定是否两处都留。

## 4. 用户故事 (User Stories)

- 作为规律训练者，我希望练完立刻看到"这次练得怎样 / 比上次进步没"，以便获得即时正反馈。
- 作为进阶用户，我希望看单个动作的全程重量曲线，以便确认自己是否在进步。
- 作为被计划驱动的用户，我希望复盘告诉我"下周该加多少重量"并一键改好计划，以便不用自己算。
- 作为长期用户，我希望看到周/周期达成率，以便保持训练节律。
- 作为减脂/增肌人群，我希望训练消耗能和饮食摄入对账，以便掌控热量缺口。

## 5. 竞品角度 (Competitors, 客观)

| 产品 | 强项 | 弱项 | 对 HiLife 的启示 |
|---|---|---|---|
| **Keep / 健身类 App** | 计划→训练→数据→社区 完整闭环；AI 动作识别；社交 | 数据解读偏"堆图表"，新手易被淹没；建议常是通用模板 | 复盘别堆图表，做"可执行的下次建议" |
| **Strong / Fitbod（海外）** | 逐动作全程曲线 + 自动渐进负荷建议（progressive overload） | 无中文社区、无饮食 | **最该借鉴"下次加多少"闭环** |
| **Apple 健身 / 华为运动健康** | 设备数据自动同步 | 训练记录需手动、无计划流 | 设备同步非个人主体短期可做，先专注记录顺手 |
| **HiLife 差异化** | AI 拍照把饮食记录成本打到最低 + 训练记录顺手 + 个人主体轻量 | 功能广度不及大厂 | 做"训练消耗 vs 饮食摄入"的独有对账闭环 |

**定位判断**：复盘不应盲目堆图表，而应学 Fitbod 做"可执行的下次建议"，并把"饮食 kcal 对账"作为独有闭环（训练消耗 ↔ 饮食摄入）。

## 6. 指标体系 (Metrics)

| 🌟 北极星 | **周训练达成率**（自然周 `trainDays / weeklyTarget`） | 直接反映复盘想促成的"节律" |

## 7. Non-goals（明确不做什么）

- 不做社交关系链 / 社区（个人主体 + 合规 ROI 低）。
- 不做 AI 全自动生成计划（数据少时易误导，且超出责任边界）。
- 不替代教练 / 康复级纠正（需免责，数据集能力有限）。
- 不堆"全景仪表盘"式图表（新手会被淹没，违背"只答三个问题"原则）。
- 不把复盘做成独立 page 顶替 list（保持"数据"tab 内聚，降低导航层级）。
- **不对照已淘汰的 `12-review.html` 任何设定去补功能**（四 tab / kcal / RPE 环 / 训练量柱图），避免复活被否方案。

## 8. 优先级与里程碑 (Roadmap)

- **前置硬约束（先于一切功能扩张）**：数据层云 DB 同步（基线 P0-1）——`trainingLogs` 全在本地 Storage，换机即丢，复盘再好看也救不回流失。
- **P0（闭环，最高价值）**：① 下次训练建议回填计划（打通 复盘→计划 回路）。**✅ 已落地**（含降重/减载 + 计划页重量入口）。
- **P0.5（口径修复，已落地）**：⑦ 进步趋势改版——纵轴 RPE→训练量、柱高 topW→容量、新增个人纪录、场次不足钩子（见 §3.4）。属于"先把没用的改对"类工作，优先级高于新功能。
- **P1（深度）**：② 任意动作全程曲线（建议落 `pages/action-detail`）；③ 周期化视角（接 cycle）。
- **P2（延展）**：④ 分享卡；⑤ 关键动作可切换任意动作；⑥ 周完成度环迁至「本次训练」tab；⑧ 可选：本场消耗 kcal（需先验证需求）。
- **贯穿**：⑨ 轻量埋点（本地先上），让上面每个功能可衡量。

> 说明：此前版本把"补 kcal/RPE 环/训练量柱图"列为 P0，那是误把淘汰稿当已确认设计。纠正后，P0 只保留"建议回填计划"这一真正由用户需求与竞争推导出的闭环项。

## 9. 风险与护栏 (Risks)

- **数据层天花板**：`trainingLogs` 全在 `wx.setStorageSync`，换机/卸载即丢 → 复盘再好看也救不回流失（基线 §4.1，应优先于功能扩张做云 DB 同步）。
- **口径回归**：verdict/周目标/自然周已用红线 + 守卫脚本守住；新增能力必须仍走单源，禁止组件内现算（已有 `verify-training-review.cjs` [I] 段递归扫 setData，新增字段须过该守卫，避免再出现 `[object Object]` 类 bug）。
- **设计系统漂移**：`DESIGN.md`(#00B86B) 与实现(#C8FF00 荧光绿) 主色不一致，新增复盘 UI 须跟实现态（荧光绿），并在 `DESIGN.md` 标注"以 `app.wxss` token 为准"。
- **需求伪证风险**：任何功能扩展须有"用户需求/竞争/基线"三方之一的论证，不得仅凭某份设计稿（尤其已淘汰稿）立项。
