这是最值得肯定的一条：小程序里"绑了一个不存在的方法"是**静默失败**（不报错、点击无反应），是最难靠真机发现的故障类型，当前不存在这种系统性风险。

## 3. 问题清单（按严重度）

### 🔴 P0-1 ·「跳过 / 结束训练」按钮点击无反应（自伤红线）

**位置**：`pages/workout/workout.wxml:209`

```wxml
<view class="pop-btn primary" bindtap="{{trainPhase === 'ready' ? 'skipTrain' : 'cancelTrain'}}">
  {{trainPhase === 'ready' ? '跳过' : '结束训练'}}
</view>
```

**根因**：WXML 的 `bindtap` **不支持 Mustache 动态事件名** —— 整个值会被当成**字面量字符串**，
点击时找不到名为 `{{trainPhase === ...}}` 的方法 → **静默无反应，且控制台不报错**。
（这条正是本项目自己记录在案的红线，全仓穷举后**仅此 1 处残留**。）

**后果（两个都是核心流程）**：
1. **准备阶段**：点「跳过」无反应 → 只能干等倒计时（`skipTrain` 实现见 `workout.js:521`，逻辑本身正确却不可达）。
2. **训练阶段**：点「结束训练」无反应 → **无法手动结束当前组计时并记录实际用时**
   （`cancelTrain` 的 `work` 分支实现见 `workout.js:529-537`；它唯一的静态绑定在 208 行，而那个按钮是 `wx:if="{{trainPhase === 'ready'}}"` → 训练阶段根本不可见）。

**修法**：挂**静态**事件名 + js 内分支（与 `pages/profile` 的 `onIdTap` 同一模式）：
```wxml
<view class="pop-btn primary" bindtap="onTrainBtn">{{trainPhase === 'ready' ? '跳过' : '结束训练'}}</view>
```
```js
onTrainBtn() { this.data.trainPhase === 'ready' ? this.skipTrain() : this.cancelTrain(); }
```
**建议同时补守卫**：`verify-*.cjs` 增加"全仓 wxml 禁止 `bind*=\"{{`"断言（1 行，永久堵住这类回归）。

### 🟠 P1-2 · 数据层天花板：单键 Storage + 1MB 硬上限

`app.js:117` `persist()` 把**整个 `globalData`** 写进唯一键 `uu_fitness_state`。

**建议**：① 短期加"存储占用自检 + 超阈值提示导出/归档"；② 中期按域拆键（logs / meals / weight 分键）；③ 终局云 DB 同步（见 §4-A1）。

## 4. 新增功能板块建议

筛选原则：**在个人主体（无支付）+ 已有云开发底座 + 主包余量紧张**这三个约束下，只做"边际成本低、结构性收益高"的事。

### A. 结构性补齐（防守 —— 不做会持续失血）

**A1 · 云数据库同步 + 自动备份｜P0｜最高优先**
- **为什么**：这是**唯一一个"不做就一定出事"**的项。当前所有数据仅存本机单键，换机/清缓存=用户资产归零，且 1MB 上限迟早触顶。
- **做什么**：`store` 落库时异步写云 DB（按用户维度），冷启动以云为准做合并；关键表先行（`trainingLogs` / `meals` / `weightRecords`）。
- **成本**：你**已经在 CloudBase 上**（云存储 + 云托管都在跑），云 DB 在免费额度内，边际成本最低。
- **验收**：清缓存重进 → 数据完整恢复；导出/导入仍作为离线兜底保留。

**A2 · 轻量埋点与"我的一周"看板｜P0｜让产品可见**
- **为什么**：现在无法回答"拍照识别被用了几次""复盘建议真被采纳了吗"。**不能衡量的功能等于没做**。
- **做什么**：本地优先的埋点（页面 UV / 拍照识别次数与耗时 / 训练完成率 / 建议采纳率），先存本地 + 自己可见的看板，再决定是否上云。
- **额外收益**：这份数据同时是你判断"哪个新板块该继续投入"的唯一依据。

**A3 · 识别结果纠错 + 本地知识库｜P1｜控 AI 成本**
- **做什么**：识别后允许改营养值并**记住**（下次同名食物直接命中）；置信度低时主动引导走条码/手输。
- **为什么**：直接降低按次计费的模型调用量，同时把"识别错→用户失去信任"变成"识别错→一次纠正后永久正确"。

### B. 留存钩子（进攻 —— 让记录变成习惯）

**B1 · 里程碑与成就体系｜P1**
- 现状已有 `dateRange.streakFromDates`（连续打卡）与 `keyActionPicks`（关键动作）。
- **升级方向**：连续 N 天 / 单动作破个人纪录 / 累计容量里程碑 → 徽章墙。**复用已有数据，几乎零新增数据模型**。

**B2 · 训练分享卡（图片）｜P1｜个人主体下最现实的增长手段**
- 个人主体不能做社交关系链，但**图片分享不受限**。
- 现状 `onShareAppMessage` 是空实现（P2-4）—— 这是**最低成本的从 0 到 1**：训练完成态生成一张带数据的卡片。
- 素材已经齐备：完成度、时长、容量、个人纪录（`buildRecords` 已有）、品牌色 `#C8FF00`。

**B3 · 训练提醒（真实现）｜P2**
- 若决定保留「训练提醒」开关（P0-2），需走订阅消息：申请模板 + 服务端定时触达。**成本不低、且受类目与模板审核约束**，建议排在 A 之后。
- 替代方案：**本地化提醒**（不做推送，改为"上次训练已 N 天"的首页提示），零审核成本。

### C. 差异化（做厚产品，但都建立在 A 之上）

**C1 · 身体维度记录（围度 / 体脂照片）｜P2**
- 与体重记录天然同构（`weightRecords` 已是「日期+数值」模型，可泛化为「日期+指标」），复用 `list` 的日期筛选与趋势图。
- 解决"体重不变但腰围在减"的经典失真，对减脂/塑形人群是高价值补充。

**C2 · 营养缺口闭环（把"推荐"变成"可执行"）｜P2**
- 你已有完整 kcal 推荐（`nutrition.recommendIntake`：Mifflin-St Jeor × 活动系数 × 目标系数）。
- **缺的是最后一公里**：不是告诉用户"目标 1800"，而是"今天还差 X 蛋白 / 差 Y 千卡"→ 点一下直接推荐加什么。
- 复用 `advice` 已有的 goal-card 与 `meals` 汇总，工作量小、感知强。

**C3 · 计划自适应（下一周期强度建议）｜P2**
- 已有 `nextSessionSuggestion`（动作级加重/降重）。**扩展到计划级**：根据近 4 周实际完成率与容量趋势，建议下一周期是"加量 / 维持 / 减载"。
- 这是从"记录工具"迈向"轻教练"的关键一步，但依赖 A1 的数据积累，**必须排在云 DB 之后**。
