这次改了什么

① 删掉「存相册发朋友圈」——通道数 = 能力数

  1. 那条通道的处理器 saveMomentsShareCard 与「保存到相册」的 saveShareCard 逐行相同（都是 _saveToAlbum(path, …)），唯一差别是成功后多弹一个 modal 讲「微信 → 发现 → 朋友圈 → 从相册选这张图」。
  2. 而 wx.showShareImageMenu 打开的就是微信原生图片转发面板，面板里本来就有「分享到朋友圈」 ⇒ 那条通道里没有一个独有能力：保存是重复的，引导是多余的。同一个能力开两个入口，用户会以为它们是两件事。
  3. 连带清理：处理器删除 · 图标 .ico-moment-sc（mask data-URI）删除 · .sc-ch 3 → 2 · 文案把「朋友圈需存到相册后自行发布」换成「点『分享给朋友』，在转发面板里可直接发到朋友圈」。
  4. 只剩两条通道后，若沿用 flex: 1 平摊，两个图标会落在 1/4 与 3/4 处、中间空出近 240rpx（看着像少了第三项） ⇒ 改 flex:1 平摊 居中 + 固定列宽 200rpx + gap 140rpx（帧 2/3/4）。

② 「取消」被遮挡：两个独立成因，一次堵掉

成因为什么会挡修法
A · 真凶
宿主页有自定义 tabBar 时没让出底栏		 组件同时挂在「数据」tab 与复盘页。自定义 tabBar 是框架级固定层，页面里 z-index 调到 2000 也压不住。 组件里另一个弹层（关键动作抽屉 .ka-mask / .ka-sheet）早就用 with-tab 处理过，分享弹层漏了。 .sc-sheet.with-tab { padding-bottom: calc(88rpx + 44rpx + safe) }； with-tab 由运行时探测（复用 _hasTabBar()，每次开弹层重探，探测异常兜底 false，最坏只是少留白）。
B · 隐患
抽屉总高没有上限		 注释写着「总高控制在 100vh 内」，但那是算出来的经验值，不是 CSS 上限。预览图是 50vh（随屏高走）， 小屏 / 文案一长就会把「取消」顶出屏幕，届时只剩点遮罩一条退路。 .sc-sheet { max-height: calc(100vh - 96rpx) }（顶部留遮罩，用户才知道能点空白关）+ .sc-preview { height:50vh; min-height:220rpx; flex:0 1 auto }（唯一可压缩项）+ 开关 / 通道 / 说明 / 取消一律 flex-shrink: 0。

几何复算（已写进守卫 verify-share-card.cjs [J]，按 1rpx = 宽/750 复算 375×667 与 375×812 两个机型）： 无 with-tab 时「取消」被盖 30 / 44 px（两个机型都一样），加 with-tab 后 0 px。 另外即使不加 max-height，最坏情况（320×568 + 有底栏 + 说明折 3 行）总高 564.7px vs 屏高 568px —— 只剩 3.3px 余量， 所以那个上限不是摆设，是随时会越界的护栏。

本稿的诚实边界

  • 分享卡缩略图在真机上是 canvas 导出的 750×H 整张图（<image> 展示，可长按调原生菜单）。 本稿按卡片版式用 HTML 重绘示意，版式细节以 canvas 出图为准。
  • 通道图标在真机走 mask-image + background-color: #0A0A0A（字形与主题无关，亮绿底铁律）； 本稿用内联 SVG 画同样的字色，两者等价。
  • 机身按 390×844（1rpx = 0.52px）。真机 375×667 上「其他各项合计」会占更大比例，抽屉更快触及上限 —— 那正是加 max-height 的原因。
  • 红色虚线框与红/绿标签是批注，不是 UI。
